# ML-микросервис прогноза посадок трамваев Москвы

Запускаемый сервис для **сохранённого лучшего решения со скором 0,89402** (результат платформы, сообщённый участником). FastAPI + NumPy, статический HTML/JS-дашборд и Leaflet, один Docker-контейнер. Сырые индивидуальные транзакции в поставку не входят.

**Область работы:** 10 маршрутов, 1 ноября — 31 декабря 2025, почасовые прогнозы; фильтрация и суммирование по дням/месяцам. Это сервис выдачи и воспроизведения зафиксированного конкурсного прогноза. Он не запускает CatBoost на новых датах или новой погоде при каждом запросе. Полный аудит требований — [AUDIT.md](AUDIT.md).

## Запуск для жюри

Из корня репозитория:

```bash
docker compose -f ml_service/compose.yaml up -d --build --wait
```

- Дашборд: <http://127.0.0.1:8088/>
- Swagger: <http://127.0.0.1:8088/docs>
- OpenAPI: <http://127.0.0.1:8088/openapi.json> и [сохранённая схема](openapi.json)
- Готовность и контрольная сумма: <http://127.0.0.1:8088/readyz>
- Полный лучший CSV: <http://127.0.0.1:8088/v1/forecast.csv>

Контекст сборки — только `ml_service/`; каталог автономен и не требует обучающего датасета, ключей, подключения к Studio или корневой Python-среды. Для первоначальной сборки нужен интернет к Docker Hub/PyPI. После сборки API и геометрия работают без внешних запросов. Подложка OpenStreetMap и Swagger UI требуют интернета.

Контейнер ограничен **2 vCPU / 2 GiB**, swap отключён через равенство memory и memory+swap limit. Два Uvicorn worker, непривилегированный UID 10001, read-only filesystem, временный `/tmp`. Порт доступен только на localhost. Внешняя публикация и аутентификация не настроены.

```bash
docker compose -f ml_service/compose.yaml logs --tail=30 ml
docker compose -f ml_service/compose.yaml down
```

## Что делает модель

При старте `app/engine.py` проверяет SHA-256 всех файлов в [manifest.json](artifacts/manifest.json), сетку ключей и календарь отмен. Затем воспроизводит v8:

1. Берёт сохранённый календарно-исторический прогноз v2 и прогноз v5 экспертов (включающий компонент CatBoost v4).
2. Согласует месячные объёмы экспертов с v2 по маршрутам.
3. Использует 25% базового и 75% согласованного экспертного прогноза; учитывает отмены движения.
4. Округляет, применяет подтверждённую публичным сабмитом поправку +3%, округляет повторно.
5. Сверяет результат **байт в байт** с лучшим CSV. Несовпадение запрещает запуск.

Итог: **14 640 уникальных route/date/hour**, целые неотрицательные `prediction`, разделитель `;`, сумма **12 902 502**. SHA-256:

```text
f2bb6115595f45a28790e6002defbcf4cc0ec6d9422c0c485c6017a0d63f9425
```

`expected.csv` — эталон для проверки; выдаваемый прогноз рассчитывается из компонентов, а не заменяется эталоном при ошибке. Файлы `base.csv` и `expert.csv` — сохранённые **выходы** моделей, не сырые транзакции и не веса обученных моделей. Сам контейнер не воспроизводит обучение этих компонентов.

Код исходной модели: [research_v2.py](../research_v2.py), [feature_models.py](../feature_models.py), [service_models.py](../service_models.py), [event_experts.py](../event_experts.py), [reconcile_forecasts.py](../reconcile_forecasts.py). Полный ML-эксперимент требует обучающих агрегатов и внешних признаков из корневого проекта. Сборка минимального пакета из уже сохранённых результатов: `python3 ml_service/tools/build_bundle.py`; для обычного запуска она не нужна.

## API

| Endpoint | Результат |
|---|---|
| `GET /v1/forecast` | JSON: строки, сумма, базовая сумма, сценарные коэффициенты, ограничения |
| `GET /v1/forecast.csv` | CSV с теми же фильтрами |
| `GET /v1/routes` | Десять поддерживаемых маршрутов |
| `GET /v1/geo/routes?route=17` | Справочная геометрия маршрута |
| `GET /v1/geo/stops?route=17` | Справочные остановки; не прогноз по остановкам |
| `GET /v1/model` | Версия, период, SHA-256 и ограничения |
| `GET /v1/sources` | Источники: использованные, экспериментальные, отсутствующие |
| `GET /healthz`, `/readyz` | Живость / загруженный и проверенный пакет |

Параметры прогноза:

- `start`, `end`: включительные даты в пределах 2025-11-01 … 2025-12-31. По умолчанию весь период.
- `routes`: повторяемый параметр; без него все маршруты. Допустимы 1, 5, 7, 11, 12, 17, 25, 26, 28, 50.
- `aggregation`: `hour`, `day`, `month`, `total`. Агрегация всегда сохраняет маршрут; поле `total` суммирует выбранные маршруты.
- `hour_from`, `hour_to`: локальные часы Москвы, начало включительно, конец исключительно. По умолчанию `[0,24)`.
- `weather_factor`, `event_factor`, `season_factor`: конечные числа 0…3, по умолчанию 1. Это **ручные сценарные множители**, а не причинные эффекты, выученные моделью. Коэффициенты перемножаются, применяются к каждому часу и округляются до агрегации.

Неизвестные маршруты/параметры, неверные интервалы, запросы отдельных остановок/участков и дат вне области возвращают HTTP 422. Часовые исходные прогнозы не меняются при сценариях. Кэш ограничен 128 комбинациями параметров на worker.

```bash
# Один день по часам для маршрута 17
curl -fsS 'http://127.0.0.1:8088/v1/forecast?start=2025-11-10&end=2025-11-10&routes=17'

# Месяц по дням, два маршрута, сценарий +10%
curl -fsS 'http://127.0.0.1:8088/v1/forecast?start=2025-11-01&end=2025-11-30&routes=1&routes=17&aggregation=day&event_factor=1.1'

# Лучший сабмит без изменений
curl -fsS 'http://127.0.0.1:8088/v1/forecast.csv' -o submission.csv
shasum -a 256 submission.csv
```

## Архитектура

```mermaid
flowchart LR
  A[История валидаций: офлайн] --> B[Агрегаты маршрут / дата / час]
  C[Календарь, погода, события, GTFS, объекты] --> D[Офлайн-признаки и модели v2 / v4 / v5]
  B --> D
  D --> E[Сохранённые прогнозы компонентов]
  E --> F[Docker: проверка пакета и восстановление v8]
  F --> G[Фильтры, сценарии, агрегация, кэш]
  G --> H[REST JSON / CSV]
  H --> I[Дашборд, график, справочная карта]
```

Граница микросервиса начинается с сохранённых прогнозов компонентов. Потоковый приём телематики, обучение и периодическое обновление модели в HTTP-процесс не встроены. Сервис не хранит пользовательские изменения и допускает несколько одинаковых реплик за балансировщиком; кэши локальны репликам. Для новой версии нужен новый проверенный пакет и перезапуск.

## Источники и ограничения

Полный реестр с рабочими ссылками и статусом — [sources.json](artifacts/sources.json), доступен и через API. Погода/календарь/события/расписания/объекты входят в компоненты выбранной модели. Используются в том числе ретроспективные значения внешних признаков будущих конкурсных дат. Это не доказательство качества при настоящем прогнозировании за два месяца без знания этих внешних значений.

**Данные автомобильных пробок, скоростей или загруженности улиц Москвы не получены.** Признаки ДТП около остановок были собраны позднее и использованы только в экспериментах; в победившую v8 не входят. Наличие источника не доказывает самостоятельного улучшения метрики; для выбранной версии нет изолированной абляции каждого источника.

Прогнозируется число посадок/валидаций, не фактическая заполненность салона. Для вместимости и выпуска нужны телематика, выходы пассажиров и модель поездок. Маршрут №5 сохранён с нулями из лучшего сабмита; это не утверждение, что пассажиров на нём нет. На новые даты, маршруты и остановки текущий результат переносить нельзя без адаптации и проверки.

План адаптации: получить актуальную историю и версии маршрутов/расписаний; собрать доступные на момент прогноза признаки; построить непересекающиеся временные проверки на полном горизонте; переобучить компоненты; проверить ошибки по маршрутам и часам; выпустить новый версионированный пакет. Для остановок нужна проверенная геопривязка валидаций и отдельный обучающий target; равномерно делить маршрутный поток по остановкам здесь не принято за ML-прогноз.

## Производительность

Замеры приведены ниже; это выдача сохранённого прогноза и расчёт сценариев, **не скорость обучения или полного CatBoost-инференса**.

Измерено 27.09.2026 на macOS ARM64, Docker Desktop, HTTP по localhost. Клиент и сервер на одной машине, 16 параллельных постоянных HTTP/1.1-соединений. Latency включает чтение тела ответа. Первые четыре прогона — по 10 секунд без ограничения скорости; последний — 30 секунд с заданным темпом 500 RPS (фактически 427 RPS). CPU нормирован на два выделенных vCPU.

| Запрос | Фактические RPS | p95, мс | CPU, % от 2 vCPU | Пик RAM, MiB | Ошибки |
|---|---:|---:|---:|---:|---:|
| День, маршрут 17, 24 часа (кэш) | 5524.69 | 5.14 | 99.83 | 146.85 | 0 |
| Месяц, все маршруты, по дням (кэш) | 4812.99 | 5.99 | 99.09 | 147.49 | 0 |
| Полный CSV, 14 640 строк (кэш) | 866.45 | 27.14 | 28.98 | 147.49 | 0 |
| Месяц, новый сценарий в каждом запросе | 810.13 | 34.14 | 100.31 | 150.75 | 0 |
| Месяц, новый сценарий в каждом запросе — ограниченный темп | 427.04 | 61.18 | 56.82 | 150.34 | 0 |

Swap во всех прогонах: **0 байт**. В ограниченном прогоне память до/после: 142,66 → 145,29 MiB. Это короткая проверка, а не доказательство отсутствия утечки за сутки. В насыщенных прогонах CPU достигает примерно 100%; они показывают максимальную измеренную пропускную способность без запаса, а не выполнение пожелания 60–80% CPU. При ограниченном темпе получили сотни RPS, p95 61,18 мс и CPU 56,82%; заданные 500 RPS полностью не достигнуты. Это локальный результат, не гарантия для другого железа, сети, полноразмерного JSON или многосуточного потока.

Исходные измерения: [benchmark.json](reports/benchmark.json), [benchmark_operating_point.json](reports/benchmark_operating_point.json). Образы в двух отчётах различаются из-за исправлений только frontend; движок и API одинаковые.

Повторить после `up --wait`:

```bash
python3 ml_service/tools/benchmark.py --container haktramv-ml-ml-1 --seconds 10 --clients 16
python3 ml_service/tools/benchmark.py --container haktramv-ml-ml-1 --seconds 30 --clients 16 --target-rps 500 --only-uncached --output ml_service/reports/benchmark_operating_point.json
```

Сборка проверена на ARM64. Базовый Python-образ зафиксирован digest, Python-зависимости — в `requirements.lock`. Leaflet 1.9.4 поставляется локально с [лицензией BSD-2-Clause](web/vendor/LEAFLET-LICENSE); карта использует OpenStreetMap с указанием авторства. Рекомендованные в задании Java/React здесь заменены Python/простым JS для самостоятельной поставки ML-контура; интеграция с отдельным backend/frontend возможна через REST.
